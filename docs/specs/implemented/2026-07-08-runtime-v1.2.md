# Runtime v1.2 — From Templates to Operating Platform

> Based on real-world deployment log analysis. Addresses architectural gaps
> identified during kordon.space integration (first consumer deployment).

## Current State Assessment

| Component | v1.1 Score | Gap |
|-----------|-----------|-----|
| Architecture Runtime | 9.5/10 | — |
| Bootstrap & install | 9/10 | State detection is heuristic |
| Canonical Schema v1 | 10/10 | — |
| Brownfield migration | 9/10 | — |
| CI/Validation | 9.5/10 | No self-validation |
| Agent Runtime | 8.5/10 | Roles exist independently, not as pipeline |
| SOP/Workflow orchestration | 7.5/10 | No executable state machine, no contracts |
| Runtime self-management | 6/10 | No self-validation, no registry |

## Problem Statement

Runtime v1.1 is a documentation infrastructure. Runtime v1.2 should be an **operating platform** with:
- Registry as single source of truth for all Runtime components
- Declarative state machine for installation lifecycle
- Machine-readable contracts (runtime + consumer levels)
- Reality Engine as standalone engine (not embedded in SOP)
- Self-validation of entire Runtime dependency graph
- Versioning and compatibility matrix for safe migrations

## Architecture

```
registry (single source of truth, versioned)
    │
    ├── roles (agents: platforms, capabilities, knowledge refs)
    ├── sops (workflows: gate, capabilities, artifacts)
    │
    ├── contracts/
    │   ├── runtime/    (installation, migration, validation, state-machine)
    │   └── consumer/   (boundaries, project-layout)
    │
    ├── engine/
    │   ├── reality-engine/  (collectors, analyzers, reporters)
    │   └── validators/      (validate-frontmatter, validate-runtime)
    │
    └── bootstrap (universal loader — reads registry, not contracts)
```

**Dependency flow:** Registry → Roles → Contracts → Validators → Bootstrap

## Technical Approach

### 1. Runtime Registry (primary object)

Add `runtime/registry.yaml` — **single source of truth** for all Runtime components. Every other component references the Registry, not the other way around.

```yaml
runtime:
  version: "1.2"

schema:
  version: 1

contracts:
  version: 1

registry:
  version: 1

compatibility:
  schema:
    - 1
  consumer:
    - "1.1"
    - "1.2"
  bootstrap:
    - 2

components:
  agents:
    - name: architecture-reviewer
      platforms: [claude-code, opencode]
      capabilities: [review-spec, review-adr, review-domain-model, review-security-model]
      knowledge: [architecture-principles, report-formats]
    - name: documentation-reviewer
      platforms: [claude-code, opencode]
      capabilities: [validate-frontmatter, validate-entity-refs]
      knowledge: [report-formats]
    - name: reality-auditor
      platforms: [claude-code, opencode]
      capabilities: [state-reconstruction, drift-analysis, architecture-extraction, attribution-analysis]
      knowledge: [evidence-model, report-formats]
    - name: adversary-checker
      platforms: [claude-code, opencode]
      capabilities: [claim-validation, assumption-analysis]
      knowledge: [audit-principles, report-formats]

  knowledge:
    - architecture-principles
    - evidence-model
    - audit-principles
    - report-formats
    - capabilities

  sops:
    - architecture-review
    - forensic-audit
    - new-feature
    - bugfix
    - new-service
    - architecture-change
    - audit
    - release
    - incident

  contracts:
    runtime:
      - installation
      - migration
      - validation
      - state-machine
    consumer:
      - boundaries
      - project-layout

  validators:
    - validate-frontmatter
    - validate-runtime

  templates:
    - architecture
    - adr
    - spec
    - audit
    - runbook
    - backlog
```

**Files:**
- `runtime/registry.yaml` — the single source of truth

**Consumers of registry:**
- `bootstrap/bootstrap.sh` — reads registry to know what exists
- `sops/planner.mjs` — reads registry for role/SOP lookup
- `engine/validators/validate-runtime.sh` — reads registry for consistency checks
- Agents — indirectly via capabilities/knowledge FM fields

### 2. Runtime State Machine

Add `runtime/state-machine.yaml` describing installation states and transitions:

```yaml
states:
  fresh:
    description: No Runtime installed
    transitions:
      - action: bootstrap
        target: installed

  installed:
    description: Runtime fully deployed
    transitions:
      - action: git-submodule-update
        target: updated
      - action: manual-edit
        target: broken

  updated:
    description: Runtime updated via submodule
    transitions:
      - action: manual-edit
        target: broken

  partial:
    description: Some components missing
    transitions:
      - action: bootstrap
        target: installed

  legacy:
    description: Old .context/runtime/ layout detected
    transitions:
      - action: migration
        target: installed

  broken:
    description: Runtime integrity compromised
    transitions:
      - action: re-bootstrap
        target: installed
```

Bootstrap reads `runtime/state-machine.yaml` and determines current state explicitly instead of heuristic detection.

**Files:**
- `runtime/state-machine.yaml` — state definitions + transition rules
- `bootstrap/bootstrap.sh` — extended with state detection (reads state-machine.yaml via registry)

### 3. Machine-Readable Contracts

Split contracts into two levels — Runtime knows itself separately from the Consumer project:

```
runtime/contracts/
├── runtime/
│   ├── installation.yaml    # what bootstrap creates, what state it expects
│   ├── migration.yaml       # v1.0→v1.1 transition rules
│   ├── validation.yaml      # what validators check, in machine-readable form
│   └── state-machine.yaml   # reference to state-machine.yaml (alias)
└── consumer/
    ├── boundaries.yaml      # what's pristine/editable/secret in consumer repo
    └── project-layout.yaml  # expected directory structure in consumer
```

**Key principle:** playbook stays as human documentation. Contracts are the machine interface. Runtime contracts describe Runtime itself. Consumer contracts describe what Bootstrap expects from the Consumer project.

### 4. Entity Catalog as Template

Bootstrap provides a template. Consumer completes it. Runtime never pretends the catalog is ready.

```
bootstrap/
├── bootstrap.sh          # extended: generates entity-catalog.md from template if missing
└── templates/
    └── entity-catalog.md # template with TODO markers
```

Bootstrap copies `templates/entity-catalog.md` → `docs/architecture/entity-catalog.md` on first run. Consumer fills in their domain entities. Runtime validates that `entity_refs` in specs/audits reference entities from this catalog.

**Why not auto-generate:** Runtime cannot know consumer's domain entities. Auto-generation would create false sense of completeness. Template + consumer completion is honest.

### 5. Reality Engine (standalone engine, not SOP)

Create `engine/reality-engine/` as a standalone engine with collectors, analyzers, and reporters. The SOP `sops/reality-audit.yaml` uses this engine but is not the engine itself.

```
engine/reality-engine/
├── README.md
├── collectors/
│   ├── architecture-inventory.sh
│   ├── entity-inventory.sh
│   ├── module-inventory.sh
│   └── dependency-graph.sh
├── analyzers/
│   ├── documentation-drift.sh
│   ├── adr-drift.sh
│   └── spec-drift.sh
└── reporters/
    └── reality-report.sh
```

The SOP `sops/reality-audit.yaml` orchestrates the engine:

```yaml
name: reality-audit
description: Automated project state reconstruction and drift detection
engine: reality-engine
steps:
  - id: 1  # Architecture Inventory (collector)
  - id: 2  # Entity Inventory (collector)
  - id: 3  # Module Inventory (collector)
  - id: 4  # Dependency Graph (collector)
  - id: 5  # Documentation Drift (analyzer)
  - id: 6  # ADR Drift (analyzer)
  - id: 7  # Spec Drift (analyzer)
  - id: 8  # Report Generation (reporter)
```

Output: `docs/audits/YYYY-MM-DD-reality-audit.md` — comprehensive state report.

### 6. Self-Validation (full dependency graph)

Add `engine/validators/validate-runtime.sh` — checks Runtime's own integrity as a complete dependency graph, not just individual documents.

| Check | What it validates | Dependency direction |
|-------|-------------------|---------------------|
| Role → Capability | Every `capabilities:` entry in agent FM exists in `knowledge/capabilities.md` | Role → Knowledge |
| Capability → Knowledge | Every capability references existing knowledge file | Capability → Knowledge |
| Knowledge exists | Every `knowledge:` short-id resolves to `knowledge/<id>.md` | Agent → Knowledge |
| Registry consistency | Every component in registry has a matching file on disk | Registry → Files |
| Contract consistency | Every contract referenced by registry exists and is valid YAML | Registry → Contracts |
| Bootstrap consistency | Bootstrap references components that exist in registry | Bootstrap → Registry |
| Workflow consistency | Every SOP `role:` has matching agent, every `capability:` exists | SOP → Agent + Knowledge |
| Template conformance | Every `engine/templates/*.md` has valid Schema v1 FM | Templates → Schema |
| Internal links | All `entity_refs` resolve to existing `id:` fields | Specs → Entities |
| Engine components | Every collector/analyzer/reporter referenced by SOP exists | SOP → Engine |

**Runs in CI:** `.github/workflows/docs-validate.yml` gets a new step.

### 7. Bootstrap as Universal Loader

Bootstrap does **not** know Runtime structure. Bootstrap reads the Registry, and the Registry tells Bootstrap where everything is.

```
bootstrap
    │
    ├── reads registry.yaml
    │
    ├── registry says:
    │   ├── where contracts are → bootstrap reads contracts
    │   ├── where validators are → bootstrap runs validators
    │   ├── where templates are → bootstrap copies templates
    │   └── where roles are → bootstrap sets up agent configs
    │
    └── bootstrap executes lifecycle
```

This means:
- Adding a new component = updating registry. Bootstrap automatically picks it up.
- No hardcoded paths in bootstrap.
- Bootstrap version 2 is the universal loader.

### 8. Compatibility Matrix

Registry declares version compatibility explicitly:

```yaml
compatibility:
  schema:
    - 1
  consumer:
    - "1.1"
    - "1.2"
  bootstrap:
    - 2
```

This means:
- Runtime 1.2 is compatible with Schema v1, Consumer v1.1 and v1.2, Bootstrap v2
- On upgrade, bootstrap checks compatibility matrix before proceeding
- Incompatible versions get explicit error instead of silent breakage

**Files:**
- `runtime/registry.yaml` — contains `compatibility:` block
- `bootstrap/bootstrap.sh` — checks compatibility on update

## Implementation Plan

| Phase | What | Depends on |
|-------|------|-----------|
| A | `runtime/registry.yaml` (primary object, versioned) | — |
| B | `runtime/state-machine.yaml` + bootstrap state detection | A |
| C | `runtime/contracts/` split (runtime/ + consumer/) | A |
| D | `engine/reality-engine/` (collectors, analyzers, reporters) | — |
| E | `sops/reality-audit.yaml` (uses engine, not implements it) | D |
| F | Entity catalog template + bootstrap generation | C |
| G | `engine/validators/validate-runtime.sh` (full graph validation) | A |
| H | CI integration (validate-runtime step) | G |
| I | Self-validation dogfood + ADR-002 | A-H |

## Consequences

### Positive
- Registry as single source of truth eliminates duplicated component lists
- Bootstrap becomes universal loader (add component = update registry)
- Contracts split clarifies what Runtime owns vs what Consumer owns
- Reality Engine is reusable (multiple SOPs can use it)
- Self-validation catches entire dependency graph degradation
- Compatibility matrix prevents silent breakage on upgrades
- Versioning on every section simplifies future migrations

### Negative
- More files in Runtime (registry, split contracts, engine directory)
- Bootstrap slightly more complex (registry-driven instead of hardcoded)
- Need to maintain registry in sync with actual behavior
- Engine directory adds indirection (SOP → Engine → files)

### Risks
- Registry drift (registry says one thing, files say another) → mitigated by self-validation (phase G)
- Over-engineering (registry for what's currently ~15 components) → keep it simple, extensible
- Engine indirection confusion → clear README explaining engine vs SOP relationship
