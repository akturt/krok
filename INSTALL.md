# INSTALL — Connecting the Underboss

> This document is intended for the consumer who has added underboss as a Git Submodule.
> The rest (`playbook/`, `documentation/templates/`, `documentation/validation/`, `documentation/schemas/`, `engine/scripts/`, `engine/reality-engine/`, `bootstrap/`, `agents/`, `knowledge/`, `sops/`, `core/`) is Underboss content, which is pulled in automatically along with the submodule.
>
> Underboss is mounted **inside `docs/`**. Only `docs/` remains at the consumer repo root — no utility directories at the root. Inside `docs/`, user-content (`architecture/`, `adr/`, `specs/`, `audits/`, ...) appears, and the system operates locally under `docs/.control/`. Underboss is **Core + Documentation Module**. See the Two-repo model section below.

> **Quick path:** Copy the prompt from [`bootstrap/DEPLOY-PROMPT.md`](bootstrap/DEPLOY-PROMPT.md) and give it to an AI agent — it will perform all the steps below automatically. Or use the one-liner: `bash <(curl -s https://raw.githubusercontent.com/akturt/underboss/master/bootstrap/install.sh)`

---

## Two-repo model

`underboss` exists in **two roles at once** — it is important not to confuse them:

### A. The `underboss` repository (product)

Underboss source code. Here directories at the root are **normal** (this is product development):

```
underboss/
├── README.md  INSTALL.md
├── core/  bootstrap/  engine/                                 ← Core
├── documentation/  knowledge/  agents/  sops/  playbook/      ← Documentation Module
├── docs/  .github/
```

Inside `docs/` lives its own dogfood (audits, specs, ADRs of the project itself).

### B. Consumer repository

You connect Underboss as a **Git Submodule inside `docs/`**. Only `docs/` remains at the consumer repo root. No `agents/`, `knowledge/`, `sops/`, `engine/`, `bootstrap/`, `playbook/`, `core/` at the root — everything is localized under `docs/.control/`. Underboss includes **Core** (core, bootstrap, engine) and **Documentation Module** (documentation, knowledge, agents, sops, playbook):

```
consumer-project/
├── README.md, package.json, src/, tests/ ...   ← normal project code as usual
├── CLAUDE.md                                    ← generated by bootstrap (snippet references docs/.control/...)
└── docs/                                        ← the ONLY root documentation directory
    ├── architecture/  adr/  specs/  audits/  backlog/  api/   ← your content (user-owned)
    └── .control/                                              ← System-owned (managed by `git submodule update --remote`)
        └── underboss/                                     ← submodule mount point (D-BR)
            ├── core/  bootstrap/  engine/                                 ← Core
            ├── documentation/  knowledge/  agents/  sops/  playbook/      ← Documentation Module
            ├── INSTALL.md  README.md
            └── ...
```

Invariant: **only `docs/` at the consumer repo root**. This is the user's mental model: "everything related to the project's documentation lives in `docs/`".

## What you get

By connecting `underboss` as a Git Submodule, your project gets:

- **Canonical Schema v1** — a single frontmatter format for all `.md` in `docs/`.
- **5-layer architecture** of documentation (architecture → ADR → spec → audit → runbook).
- **Lifecycle from path** for spec/api — document status is determined by the folder, not an editable field.
- **CI guard** — no `.md` without canonical frontmatter will enter the repository.
- **Bootstrap** — a single command creates the `docs/` + `.context/` + `CLAUDE.md` skeleton snippet.
- **install.sh** — one-liner installer: `bash <(curl -s ...)`
- **Migration script** — for brownfield repositories, migration of legacy frontmatter to Schema v1.
- **Validators** — `validate-frontmatter.sh` (local + CI) + `validate-integrity.sh` (dependency-graph validation).
- **Templates** — canonical templates for all document types (6 files in `documentation/templates/`).
- **Schema** — `frontmatter.schema.json` (JSON Schema for IDEs/agents).
- **Agent roles** — ready-made role configs in `agents/{claude-code,opencode}/`: `architecture-reviewer`, `documentation-reviewer`, `reality-auditor`, `adversary-checker`. Place them in `.claude/agents/` or `.opencode/agents/` (optional).
- **Knowledge layer** — `knowledge/` with shared principles (architecture-principles, evidence-model, audit-principles, report-formats, capabilities). Roles reference them by short-id.
- **SOPs** — 10 declarative YAML descriptions of standard processes (`new-feature`, `bugfix`, `new-service`, `architecture-change`, `audit`, `release`, `incident`, `architecture-review`, `forensic-audit`, `reality-audit`). The `sops/planner.mjs` planner prints a DAG of steps with roles and **artifact contracts** (consumes/produces).
- **Core** — `core/`, `bootstrap/`, `engine/` — registry, installation state machine, contracts, reality engine.
- **Documentation Module** (v1.9) — the documentation module: `documentation/`, `knowledge/`, `agents/`, `sops/`, `playbook/` — templates, validation, knowledge, roles, SOPs.
- **Registry** (v1.9) — single source of truth for all Underboss components (`core/registry.yaml`).
- **Installation State Machine** — explicit installation states and transitions (`core/installation-state-machine.yaml`).
- **Contracts** — product- and consumer-level contracts (`core/contracts/`).
- **Reality Engine** (v1.9) — engine for reconstructing project state and detecting drift (`engine/reality-engine/`).

```bash

git clone --depth 1 https://github.com/akturt/underboss.git /tmp/underboss

## Step 1 — Connecting the submodule

From the root of your project:

```bash
# mount INSIDE docs/
mkdir -p docs/.control

git submodule add \
    https://github.com/akturt/underboss.git \
    docs/.control

# Pin the master branch in .gitmodules (so `--remote` pulls master, not detached HEAD)
git config -f .gitmodules submodule."docs/.control".branch master

git commit -m "chore: add Underboss via submodule"
```

After this, `.gitmodules` contains:

```ini
[submodule "docs/.control"]
    path = docs/.control
    url = https://github.com/akturt/underboss.git
    branch = master
```

# then update paths in .github/workflows/docs-validate.yml, CLAUDE.md, .context/agent-entry.md
# (a re-run of the new bootstrap will do this idempotently)
```

## Step 2 — Cloning with submodules (for other contributors)

```bash
# New clone — with submodules right away
git clone --recurse-submodules <your-repo-url>

# Existing clone — initialize submodule
git submodule update --init --recursive
```

## Step 3 — Running bootstrap (once)

Bootstrap creates the `docs/` skeleton, `.context/` stubs, and `CLAUDE.md` snippet in your project. It is idempotent — safe to run again.

```bash
# Linux / macOS / WSL
bash docs/.control/bootstrap/bootstrap.sh

# Windows (PowerShell)
powershell -File docs\.control\bootstrap\bootstrap.ps1
```

What bootstrap will create:
- `docs/{architecture,adr,specs/{drafts,approved,implemented,superseded},audits,backlog,api}/` — the 5-layer structure.
- `docs/architecture/entity-catalog.md` — the entity catalog template (filled in by the consumer).
- `docs/architecture/invariants.md` — the architectural invariants template (created by bootstrap on first run).
- `.context/{project.yml,boundaries.yml,agent-entry.md}` — stubs for the AI agent (fill in for your project).
- `CLAUDE.md` (or `AGENTS.md`) — snippet with Underboss rules.
- `.github/workflows/docs-validate.yml` — CI guard + validate-integrity.

If `docs/` already exists, bootstrap does NOT overwrite existing files — it only creates missing ones. `.gitkeep` for empty directories.

## Step 4 — CLAUDE.md snippet

Bootstrap automatically adds this block to `CLAUDE.md` (or creates it):

```markdown
## Underboss

Underboss is connected as a Git Submodule:

    docs/.control/

Before any change to `docs/`:
1. Study `playbook/playbook-v2.md` (target model)
2. Use `documentation/templates/` — do NOT copy templates into the project
3. Follow `documentation/schemas/frontmatter.schema.json`
4. Run `documentation/validation/validate-frontmatter.sh` before commit
5. For brownfield migration, follow `playbook/migrate-legacy.md`
6. For typical processes, pick a SOP in `sops/` and run `sops/planner.mjs <name>` — call roles by name
7. If task involves architectural review — see `sops/architecture-review.yaml`; foundation is `reality-auditor` BEFORE `architecture-reviewer`.
8. Common knowledge bases live in `knowledge/` (`architecture-principles`, `evidence-model`, `audit-principles`, `report-formats`, `capabilities`) — roles reference them by short-id, not inline.
```

If you already have a `CLAUDE.md` with other content, the snippet is appended at the end. Verify that the `## Underboss` section is not duplicated (bootstrap is idempotent about this).

Alternative entry files: `AGENTS.md` (opencode convention) or `.opencode/config` — the snippet is identical, just substitute your own filename.

## Step 5 — Fill in `.context/project.yml`

Bootstrap creates a stub. Replace the placeholders with the specifics of your project:

```yaml
project:
  name: my-project
  description: "One-sentence: what this project is"
  domain: example.com
  maintainer: team-name
  repository: https://github.com/org/repo

stack:
  backend: [FastAPI, Python]
  database: [PostgreSQL 17]
  infrastructure: [Docker Compose, Traefik]

directories:
  key:
    app/: "Main code"
    infra/: "Infrastructure"
    docs/: "Documentation"
```

This information is Layer 0 for the AI agent. Without it, the agent cannot tell which project it is working in.

---

## Step 6 — Fill in `.context/boundaries.yml`

Bootstrap creates a stub with `docs/.control/` as `pristine` and `docs/` (the rest) as `editable`. Extend it for your project:

```yaml
boundaries:
  pristine:
    - path: vendor/
      reason: "third-party, tracked upstream"
    - path: docs/.control/
      reason: "Underboss submodule (managed by git submodule update --remote), NEVER edit in-place"

  editable:
    - path: app/
      reason: "core application code"
    - path: docs/
      reason: "all user-authored documentation (architecture, adr, specs, audits, backlog, api)"
    - path: infra/
      reason: "infrastructure config"

  generated:
    - path: .env
      source: .env.example
      reason: "created by bootstrap from template"

  secret:
    - path: .env
      note: "passwords and tokens"
    - path: "*.key"
      note: "private keys"
```

**Critical:** the path `docs/.control/` MUST be `pristine`. It is a submodule — never edit its contents in-place; only update the submodule as a whole (Step 7).

## Step 7 — Create the first document

Copy a template from Underboss into your `docs/`:

```bash
# ADR (Architecture Decision Record)
cp docs/.control/documentation/templates/adr.md docs/adr/001-orchestrator-choice.md
# Edit the frontmatter (id, status, date, owners) and body

# Spec (uses lifecycle from path)
cp docs/.control/documentation/templates/spec.md docs/specs/drafts/$(date +%Y-%m-%d)-new-api.md
# status: draft → must match the drafts/ directory

# Architecture
cp docs/.control/documentation/templates/architecture.md docs/architecture/README.md

# Audit
cp docs/.control/documentation/templates/audit.md docs/audits/$(date +%Y-%m-%d)-initial.md
```

Details on creating and the lifecycle of documents are in [`playbook/playbook-v2.md`](playbook/playbook-v2.md).

## Local validation before commit

Before committing `.md` files in `docs/`:

```bash
# Check (like in CI)
bash docs/.control/documentation/validation/validate-frontmatter.sh

# Validate knowledge/ (if you use a custom knowledge)
ROOT=knowledge bash docs/.control/documentation/validation/validate-frontmatter.sh knowledge

# Validate the Underboss dependency graph
bash docs/.control/documentation/validation/validate-integrity.sh
```

CI (`docs-validate.yml`) does the same automatically — but local validation gives a faster feedback loop.

## Updating Underboss

### Option A — manually (recommended at first)

```bash
# Pull the latest changes from underboss master
git submodule update --remote --merge

# Record the new SHA in your repo
git add docs/.control
git commit -m "chore: update Underboss"
```

Takes five seconds. By default the `master` branch is pulled (see `branch = master` in `.gitmodules`).

### Option B — via bootstrap

```bash
bash docs/.control/bootstrap/bootstrap.sh
```

Bootstrap will automatically detect the version and update the components.

### Option C — Dependabot gitsubmodule (auto-PR)

GitHub can track Git Submodule updates and create PRs automatically:

```yaml
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "gitsubmodule"
    directory: "/"
    schedule:
      interval: weekly
    commit-message:
      prefix: "chore"
```

Dependabot creates a PR with the new submodule SHA on every change to `underboss/master`. You review and merge it — no automation touches master without your approval.

### Rollback

```bash
# To a specific underboss SHA
cd docs/.control
git checkout <commit-sha>
cd ../..
git add docs/.control
git commit -m "chore: pin Underboss to <commit-sha>"
```

A specific SHA = reproducibility. Rollback is trivial.

## Brownfield — you already have `docs/` with `.md` files

If the repository already has documentation: do not run bootstrap (it will not overwrite existing files, but it also will not migrate them). Instead of bootstrap, follow [`playbook/migrate-legacy.md`](playbook/migrate-legacy.md) — there is a step-by-step agent prompt for brownfield migration.

Briefly: run `engine/scripts/migrate-legacy.mjs`, then clean up forgotten `docs/archive/` until the validators pass.

## What NOT to do

| ❌ Don't | ✅ Do this instead |
|---------------|----------------------|
| Copy templates into `docs/` and keep duplicates in the repo | Use templates as the source of truth: `cp docs/.control/documentation/templates/<type>.md docs/<type>/...` once |
| Edit files in `docs/.control/` in-place | Update the submodule as a whole; do not touch the contents |
| Pin the submodule to a detached HEAD without recording it in `.gitmodules` | Always use `branch = master` in `.gitmodules` so `--remote` works |
| Create `.md` without `cp docs/.control/documentation/templates/...` | Canonical frontmatter cannot be written "from scratch" — start from the template and fill in the 6 fields |
| Use legacy fields (`author`, `title`, `created`, `lifecycle`, `referenced_by`, `supersedes_adr`, `excludes-from-scope`) | Replace: `author`→`owners`, `title`→body H1, `created`→`date`, `lifecycle`→computed from path |

## SOP — Standard Operating Procedures (if you use processes)

If you want to follow standard development processes (New Feature / Bugfix / Release / Incident), Underboss contains declarative descriptions in `sops/*.yaml`. Each SOP is a YAML describing steps as a DAG with references to roles from `agents/` or `gate: manual` (human step).

```bash
# List available SOPs
node docs/.control/sops/planner.mjs

# Execution plan for new-feature (shows parallel groups, roles, and artifacts)
node docs/.control/sops/planner.mjs new-feature --platform claude-code

# Only AI agent roles (without manual human steps)
node docs/.control/sops/planner.mjs new-feature --hide-human
```

An SOP is a checklist, not an orchestrator. planner.mjs is a DAG-printer (not an executor). You read the plan, manually invoke roles via slash commands in agents (e.g. `/architecture-reviewer` in Claude Code or `@architecture-reviewer` in opencode), and perform manual steps yourself. There is no scheduler.

### Artifact contracts

SOPs use explicit `consumes:` and `produces:` fields — controlling the data-flow between DAG steps (not just control-flow via `depends_on:`). Canonical artifact names: `reality-report`, `architecture-findings`, `documentation-report`, `validated-findings`, `forensic-report`. See `knowledge/report-formats.md` and `sops/architecture-review.yaml` / `sops/forensic-audit.yaml`.

### Reality Audit (v1.9)

The `reality-audit.yaml` SOP uses the Reality Engine to reconstruct project state and detect documentation drift. To run:

```bash
# Manually via the agent
# see sops/reality-audit.yaml — 8 steps with collector → analyzer → reporter pipeline
```

Custom SOPs for your project's specific processes should go in `.context/sops/` of your repository (outside the submodule); Underboss will not override them.

## Troubleshooting

### `git submodule update --remote` pulls nothing

Check that `.gitmodules` contains the line `branch = master`. If it is missing, add it:

```bash
git config -f .gitmodules submodule."docs/.control".branch master
```

### CI fails on legacy fields in prose/code-block

The CI guard checks **only frontmatter**, not the whole file. Mentions of `lifecycle:` in a table or `title:` in a code example should not break CI. If it breaks, check that you have the latest Underboss version (`git submodule update --remote`).

### Bootstrap overwrote my `CLAUDE.md`

No. Bootstrap checks for the presence of the `## Underboss` section and appends only if it is absent. Revert with `git checkout CLAUDE.md` and add the snippet manually if needed.

### I want different entry files for different AI platforms

Bootstrap creates `CLAUDE.md`. For opencode, symlink or copy it to `AGENTS.md`. The snippet content is identical. Details about roles are in `agents/README.md`.

### validate-integrity.sh fails with entity_ref errors

This is expected for concept entities (`agentic-layer`, `schema-v1`, etc.). They resolve via registry components and the concept namespace. If the error is elsewhere, check that `entity-catalog.md` is filled in.

## What is implemented

- **Core** — `core/`, `bootstrap/`, `engine/` — the core of the system: registry, installation state machine, contracts, reality engine, dependency-graph validation.
- **Documentation Module** — `documentation/`, `knowledge/`, `agents/`, `sops/`, `playbook/` — the documentation module: templates, validation, knowledge, roles, SOPs.
- **Registry** — single source of truth (`core/registry.yaml`).
- **State Machine** — explicit installation states (`core/installation-state-machine.yaml`).
- **Contracts** — product- and consumer-level contracts (`core/contracts/`).
- **Reality Engine** — engine for reconstructing state (`engine/reality-engine/`).
- **validate-integrity.sh** — dependency-graph validation (10 categories).
- **entity-catalog.md** — the entity catalog template for consumers.
- **install.sh** — one-liner installer.
